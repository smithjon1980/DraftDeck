# BOSS Order of Operations

## The right work in the right order

**Version:** 0.2.1 — Day Zero instructional script and frame sequence, 9 October 2026.

**Purpose:** Teach learners to identify a prerequisite, recognize the consequence of skipping it, and recover a bounded operation. Placement: Day Zero foundation, introducing and applying prerequisite ordering within PRIME. This draft retains the shared-frame contract; it does not report a rebuilt slide deck.

**Learning evidence:** Given a workshop source and a proposed announcement, the learner identifies an unsupported room number, records it as unknown, completes work that does not depend on it, and names the evidence and authorization needed for the affected release.

**Teaching pattern:** Familiar consequence → simple comparison → technical analogy → BOSS operating sequence → worked mistake → corrected route → learner practice → recovery → recap. The supplied Mighty Owl transcript informs this teaching pattern; the narration below is newly written. No video or audio was inspected for this draft.

## Original narration

### 01 — Same ingredients, different sequence

Imagine preparing pancakes. You have eggs, flour, and milk. But instead of combining them into batter, you cook the eggs first. You have used familiar ingredients, yet you have started a different dish. The sequence changed what the actions produced. In a work process, having all the right pieces is only the beginning. We also need to know which action depends on another action being completed first.

### 02 — One expression, one precedence rule

Consider twelve minus two times four. If you subtract first, you get ten, then multiply by four and report forty. But the expression requires multiplication before subtraction. Two times four is eight. Twelve minus eight is four. The mistake was performing a valid arithmetic operation at the wrong point in the calculation.

### 03 — Grouping changes the task

Now place parentheses around twelve minus two. This changes the expression. Subtract inside the parentheses first, then multiply ten by four. Forty is correct for this new expression. That distinction matters: following an instruction and silently changing an instruction are different operations. Before executing a task, establish exactly which task you have been given.

### 04 — Computer startup depends on preparation

Computer startup offers another example. In the UEFI boot process, a boot manager can load an operating-system loader. The loader uses firmware services before taking control of the system. Preparation and transfer have dependencies. We borrow that idea for this lesson: check the required condition before the dependent action. BOSS is a work framework; the startup example illustrates prerequisites, not a technical implementation of BOSS.

### 05 — Put the work into PRIME

The BOSS operating sequence is PRIME: Package, Route, Inspect, Move, and Establish Delivery. Package identifies the cargo. Route establishes where it belongs and how it will travel. Inspect checks the source, constraints, and handling requirements before or during movement. Move executes the permitted work. Establish Delivery checks what arrived, its condition, and the authority for release. The order comes from dependencies, not from the acronym. Inspection may occur before or during movement, and recovery can return us to an earlier stage. These stages help us locate dependencies and recover when one is missing.

### 06 — A polished announcement can still be unsupported

Suppose a workshop source gives a date and a session title, but no room number. An operator requests a public announcement. The model returns fluent copy with a plausible room number, and the operator publishes it before comparing the draft with the source. The unsupported claim is already public when the comparison catches it. The problem is both the unsupported field and the release performed before the required checks.

### 07 — Package and route before dependent execution

Start again with the actual source and its version. Use the shared frame to identify the observable objective, inputs, exact destination, permitted actions, unknowns, completion criteria, and return format. Keep all ten fields in the working agreement. Then route the work to the appropriate tool and destination. Permission to prepare a draft may cover drafting. Public release must fall within the human's authorization for that action and destination.

### 08 — Inspect the missing operand

Read the source and compare it with the requirements. The room number is absent. Record that absence as an unknown; do not supply a likely room. A missing room number does not prevent every useful action. You can still inventory the source or prepare a draft that clearly preserves the unresolved field. Hold the action that depends on a confirmed room number, and identify how that fact can be supplied and checked.

### 09 — Return only what the contract supports

Execute the bounded operation. If the return format requires structured data, represent the unknown explicitly. A null room-number value can preserve the gap, accompanied by a statement that the source did not provide it. Structure makes a field easier to inspect; it does not establish that its contents are correct. Apply the agreed checks to both the record and any accompanying commentary.

### 10 — Establish delivery and apply authority

Now check the destination. Arrival evidence supports arrival. A source comparison supports the specific content checks it performed. Record the check, its result, and the verifier. Keep verification separate from release authorization. Existing authorization may already cover this artifact, action, and destination. If it does, apply that authority within its scope. If it does not, the affected release waits. A populated tag or a completion statement does not supply missing evidence or grant permission.

### 11 — Locate what can proceed

Try two cases. First, a draft contains a room number that you cannot find in the supplied source. Can you release the room-dependent announcement? What useful work can continue? Second, a receiving system confirms that a file arrived. Does that establish that its contents match the source? Record the claim each piece of evidence supports, then identify the next check. Avoid treating every unresolved fact as a failure of the whole task.

### 12 — Repair the affected dependency

For the first case, preserve the unknown, hold the affected release, obtain an authoritative room number, and repeat the relevant comparison. For the second, inspect the received contents before claiming fidelity. If something unsupported was already published, document it and correct the destination; a later check cannot undo the earlier exposure. PRIME gives us a route through the work and a place to return when a prerequisite is missing. The accountable human controls the next bounded action.

## Author and production notes

- Use the existing PRIME vocabulary. The retrieved `prime-process.md` describes itself as a Candidate Canonical Reference; this draft does not promote its status or introduce another acronym.
- PRIME is a dependency-oriented process, not a ban on iteration. Inspect may occur before or during movement; destination verification also occurs after movement. Recovery returns to the affected stage.
- The ten shared-frame fields form a working agreement. Their list order is not a universal execution schedule. Keep the shared frame, response message, verification tag, and operation-status namespaces distinct.
- Mathematical precedence determines the result of a specified arithmetic expression. A governed software workflow does not guarantee identical generated outputs, truth, or successful delivery.
- The computer example uses UEFI terminology for the specific technical description. Do not relabel UEFI as legacy BIOS or imply every computer has one identical startup implementation. The point of comparison is prerequisite ordering.
- Two human operators can follow the same governing sequence and still produce different drafts. Evaluate their claims and evidence against the same contract rather than requiring identical prose.
- The proposed public-announcement incident is hypothetical. It is not a report of an observed BOSS execution. Keep illustrative source, draft, and evidence visually labeled.
- Use actual, legible typeset records. Avoid software anatomy, retired role/schema vocabulary, pseudo-text records, and unsupported numerical authority claims. Keep human authority explicit.
- Do not copy the arithmetic error in the supplied transcript around 03:33. For `2 × (5 + 3) × 2 + 4`, the result is `2 × 8 × 2 + 4 = 32 + 4 = 36`, not 40.
- This draft provides a teaching script. It does not resolve the NotebookLM input inventory, confirm audio transcription, or certify a future generated video. Inspect actual output before making those claims.
