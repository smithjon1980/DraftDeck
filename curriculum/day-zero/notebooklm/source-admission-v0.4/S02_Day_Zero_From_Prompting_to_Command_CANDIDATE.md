# BOSS Day Zero — From Prompting to Command
## Understanding the Systems Behind Governed AI

**Curriculum master compilation · candidate v0.4 · not yet admitted to NotebookLM**

### Learning promise
Day Zero trains a novice to specify, manually carry, inspect, and account for information exchanged between AI systems. The learner finishes with a reproducible handoff packet that can later become a workflow specification. The aim is accountable system operation, not merely better prompt wording. This lesson takes place on a local device using ordinary tabs, files, and visible records; no installed automation, server, API credential, or specialist infrastructure is required.

**Governing sequence: Manual First. Automated Second. Governed Always.**

### 01 · From passive use to accountable operation
A passive user requests an answer and treats fluent output as completion. An accountable operator establishes the actual task, available inputs, permissions, destination, acceptance criteria, and evidence. They distinguish between what a system claims, what it attempted, what it actually performed, and what can be verified. Command is accountable direction within real permissions; it does not imply ownership of a model's internal behavior.

*Illustration:* Asking two chat systems to summarize a document does not establish that either read the complete document. Before evaluating summaries, verify the document is actually available and readable to each system. Different results are an inspection signal, not immediate proof that either system is malicious or defective.

### 02 · The Information Supply Chain
Treat information as a documented shipment for teaching purposes. Identify the sender, origin, payload, manifest, destination, handling restrictions, custody transfer, receiving inspection, and acceptance receipt. The analogy does not turn data into physical freight, nor does it establish literal equivalence with logistics law or network layers. A copied instruction is a package; sending it is movement; seeing it appear is a receipt; checking it against the source is verification; releasing an approved conclusion is a distinct authority decision.

### 03 · Boundaries, permissions, and authority
Before touching an external tool, establish which actions are allowed: read, transform, draft, publish, purchase, execute, or alter source data. Possession of an API token, installed plugin, configured integration, or active session is not a blanket delegation of authority. Record the person or institution responsible for release. When scope exceeds expertise or creates material security, privacy, legal, clinical, or financial exposure, seek qualified review before operational release.

### 04 · The Missing Interface
Two independently operated AI chats generally do not share memory, credentials, files, tool access, or verified state by default. A human may pass context from one to another, but copying text cannot magically transport hidden context or capabilities. The learner must move a **shared frame** describing the task and receive back an explicit account of what was understood. An acknowledgement demonstrates receipt of text, not equivalence of internal state.

### 05 · Source authentication and provenance
Inspect the actual content rather than trusting titles or upload badges. Capture source title, origin, version, date, rights/usage permission, hash where practical, and a manifest of included sections. Preserve original source text and label derived notes as derived. An earlier draft can explain history but must not silently override an accepted version. If a source is missing, conflicting, garbled, or inaccessible, mark the missing fact UNKNOWN or NOT ESTABLISHED.

### 06 · A minimal shared frame
Prepare a packet containing: RUN_ID; objective; named source inputs and versions; destination; defined terms; permitted actions; prohibited actions; known unknowns; return format; acceptance criteria; and requester identity. Ask the receiving system to restate its understanding, identify missing operands, and describe unavailable capabilities. Authorize only bounded actions. Do not infer consent for new ones.

### 07 · Manual governed handoff
The learner operates two tabs and a local evidence sheet. First prepare the shared frame; second verify the receiving destination; third copy only the approved packet; fourth request a restatement; fifth correct discrepancies; sixth execute a read-only bounded exercise; seventh obtain a receipt; eighth compare its claims to the original source; ninth log unresolved issues. Recover only missing or failed items rather than resending everything blindly.

### 08 · IPOS: the process specification
The instructional worksheet uses an IPOS diagnostic: **Inputs, Process, Outputs, Standards**. Inputs identify the source and permissions; Process describes reproducible steps and boundary checks; Outputs specify what the receiver must return; Standards define pass/fail evidence and prohibited outcomes. IPOS is a local design vocabulary for the course; do not equate it to a universal networking protocol. An IPOS worksheet becomes a proposed workflow specification for later automation, not evidence that automation has been built.

### 09 · Distinguishing AI models, APIs, plugins, MCP, and skills
An AI model generates responses from provided context and learned patterns. An API is a defined programmatic interface. A plugin or connected app packages accessible capabilities and authorized interactions with an external service. An MCP server exposes compatible tools or resources through the Model Context Protocol, but its presence alone does not prove a working connection. A skill is a reusable set of procedural instructions or resources describing how to perform a task. These layers differ: instructions are not permissions; a registration is not execution; and execution is not verified correctness.

### 10 · The transfer manifest and custody record
Prepare a manifest listing each source item, format, version, expected destination, transformations allowed, and acceptance checks. At transfer, record timestamp or event order, sender, recipient, exact payload or durable pointer, and any deviations. At receipt, compare item counts, lengths, quoted passages, and hashes where appropriate. If a passage is absent or malformed, record the discrepancy as a failure, not as an implied successful transfer.

### 11 · Split-Signal Errors and exception states
A Split-Signal Error occurs when operational statements disagree across sources, instructions, receipts, or system outputs. Examples: the manifest says six sections but the receiver lists five; a draft says a release passed while evidence shows it remains pending; a tool reports a configured connection but no invocation. Do not resolve a conflict by selecting the more confident statement. Identify the competing claims, inspect primary evidence, mark the state HOLD or NOT ESTABLISHED, and request a bounded corrective action.

### 12 · Verification: what counts as proof
Evaluate separate predicates: source was readable; transfer occurred; destination received expected content; tool actually executed; output was semantically correct; permission was valid; human release was approved. One passing predicate does not imply the others. Use positive and negative test cases. Preserve the exact error and evidence record; a polished summary is not a substitute for underlying evidence.

### 13 · PRIME: controlled movement
PRIME is a course-level process mnemonic: **Package, Route, Inspect, Move, Establish Delivery**. Packaging defines scope and markings; Routing identifies destination and handling; Inspection checks the source and controls; Moving executes the permitted transfer; Establishing Delivery records accepted destination state with evidence. A valid receipt does not, by itself, establish that the transferred claim is true. Reinspection can occur at multiple boundaries, and failures can stop the process before release.

### 14 · PARCELS: allocating responsibilities
PARCELS denotes the seven candidate architecture layers: **Platform, Attachment, Routing, Carriage, Exchange, Language, Service**. It answers where a responsibility or interface belongs, whereas PRIME names the process stages. It is not a literal replacement for OSI or another formal networking standard. Students should map one feature to each relevant layer without claiming that all implementations must adopt this organization.

### 15 · The Tunnel Protocol
The six-step educational reconstruction is **Intake → Discovery and Classification → Tunnel Boundary → Package and Route → Inspect and Verify → Authorize and Establish**. Use it to decide what may enter a tool's source context. Reject superseded text as governing authority; preserve quarantined historical materials separately; allow explicit exception reports; and retain a traceable path from source to verified output. This specification is a candidate synthesis awaiting comparison to earlier Tunnel Protocol PDFs.

### 16 · The Commercial Release Gateway
A release checkpoint assesses source legitimacy, rights, claims, quality, and responsible authorization before a commercial artifact is published. Distinguish a described gate, a simulated gate, an implemented gate, and a gate whose enforcement has been verified. Assignment 06 execution has not been independently established for this curriculum. Never describe its live enforcement as confirmed without an authenticated execution record.

### 17 · Recovering from failure
Acknowledge what succeeded and what failed. Keep original evidence. Do not overwrite failed records with later success claims; append recovery steps. If one section failed, retransmit only that section with its manifest identifier and ask for a new receipt. If the cause is a missing operand or unauthorized tool, stop and obtain missing source or proper authorization rather than improvising.

### 18 · The role of constraints and discipline
A successful workflow needs precise scope, reproducible instructions, meaningful exclusions, and verifiable completion rules. Unbounded generation often increases rework because attractive outputs conceal omissions. Encourage creative exploration inside defined design boundaries, but never let presentation substitute for technical validation, factual support, or human release authority.

### 19 · Manual work becomes a Windmill specification
Day One may introduce Windmill as a workflow orchestrator. Translate IPOS rows into workflow steps, explicit inputs, branch conditions, approvals, error handling, outputs, logs, and tests. A manual verified sequence supplies requirements, not a production-ready implementation. Revalidate security, credentials, permissions, and evidence when execution moves from a human-operated exercise to software automation.

### 20 · Toward independent infrastructure
A self-managed VPS can host some control-layer tools, workflow services, and databases using containers when the provider and plan support the required access and capacity. External AI inference can remain separately supplied through APIs; local inference can be considered later if resources permit. Ownership of execution infrastructure can improve portability without removing vendor dependencies, maintenance obligations, security responsibilities, or professional review requirements. Bluehost is a candidate deployment target, not proof of a completed deployment.

### 21 · Final learner assessment and next-day bridge
Submit (a) source manifest, (b) shared frame, (c) IPOS worksheet, (d) sent packet, (e) receiver's verbatim receipt, (f) reconciliation report, (g) unresolved items, and (h) release decision. Explain exactly which claims are established and which remain unknown. Demonstrate how each verified manual step maps to a candidate Windmill workflow node. Do not grant yourself a qualification merely for finishing the exercise.

## Reflection and assessment questions
1. Which source did the receiver actually read, and what evidence proves it?
2. What changes when a tool has a connector but lacks authorized access to a particular resource?
3. Which statement in the receipt is a claim rather than verified evidence?
4. Can a transferred sentence be accurately delivered but factually false? Explain.
5. When does a source conflict justify HOLD rather than correction by guesswork?
6. What requires specialist review before a workflow is exposed to outside users?
7. Which IPOS fields map directly into Windmill, and which require new implementation decisions?
8. Who has authority to approve a commercial release, and what must they inspect?
