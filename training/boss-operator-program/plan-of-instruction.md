## 1. Purpose

This Plan of Instruction (POI) defines the curriculum architecture, instructional sequence, qualification model, module contract, artifact requirements, competency map, assessment model, instructor requirements, and release controls for the **BOSS Operator Program**.

The POI exists to operationalize the compile chain:

~~~text
BOSS DOCTRINE
      ↓
PLAN OF INSTRUCTION
      ↓
INSTRUCTOR / STUDENT TREATMENTS
      ↓
MEDIA
      ↓
PRACTICE
      ↓
ASSESSMENT
      ↓
QUALIFICATION
      ↓
CERTIFICATION / CREDENTIAL
~~~

The POI is canonical **training material**, not doctrine.

It is downstream from the BOSS doctrine stack and must preserve doctrinal meaning while converting it into teachable, assessable, releasable instruction.

> **Nothing gets built without traceability to the POI.**

## 2. Authority and Training-Material Boundary

### 2.1 Doctrine remains upstream

The course may explain, sequence, visualize, practice, test, and simulate BOSS doctrine.

The course may not:

- redefine doctrine;
- invent authority that doctrine does not grant;
- weaken a prohibition for instructional convenience;
- turn an example into a governing rule;
- replace a doctrinal distinction with a simpler but false teaching shortcut;
- treat a training artifact as more authoritative than its cited doctrine dependency.

### 2.2 Conflict rule

When a downstream training artifact conflicts with:

1. this POI, the POI controls;
2. canonical doctrine, doctrine controls over both the POI and the artifact.

### 2.3 Required traceability

Every module must identify:

- doctrine dependencies;
- canonical vocabulary;
- terminal objective;
- enabling objectives;
- artifact outputs;
- assessment evidence;
- remediation path;
- release state.

Every learner-facing artifact must be traceable to one or more module objectives.

Every assessment item must be traceable to an objective.

## 4. Program Chain

The BOSS Operator Program begins before Day Zero.

The complete chain is:

~~~text
PRE-ENTRY
      ↓
DAY ZERO
      ↓
MODULES 01–07
      ↓
FINAL INTEGRATED SIMULATION
      ↓
QUALIFICATION
      ↓
CERTIFICATION
      ↓
CREDENTIAL
      ↓
CONTEXT-SPECIFIC AUTHORIZATION
~~~

The following states are deliberately distinct:

> **TRAINED ≠ QUALIFIED ≠ CERTIFIED ≠ CREDENTIALED ≠ AUTHORIZED**

These distinctions are seated on the broader BOSS rule:

> **CAPABILITY ≠ PERMISSION.**

### 4.1 Trained

Required instructional material has been completed.

### 4.2 Qualified

Observed performance establishes that the learner meets the minimum capability standard for the defined operator role.

### 4.3 Certified

The program authority formally attests that the learner has met the defined qualification standard.

### 4.4 Credentialed

A durable record binds identity to the relevant certification or qualification state.

### 4.5 Authorized

A specific operational environment, owner, organization, or authority grants permission to perform a specific class of work.

Certification or credentialing does not imply universal authorization.

## 9. Module Objectives

### 9.1 Module 01 — Package Operations

**System Question:** What exactly is being handled?

**Terminal Objective:**  
Given an operational request, the learner can produce a bounded work package with an established destination, required inputs, constraints, package scope, and acceptance conditions without silently expanding authority or inventing missing requirements.

**Enabling Objectives:**

The learner can:

1. distinguish mission from package;
2. distinguish request from package;
3. identify package boundaries;
4. identify required inputs and dependencies;
5. define the destination;
6. define acceptance conditions;
7. identify unresolved assumptions;
8. recognize an over-broad package;
9. reduce package scope without reducing destination scope;
10. distinguish package identity from conversation context;
11. apply minimum-necessary scope when appropriate.

**Primary Doctrine Dependencies:**

- Logistics Framework;
- Bioscillate PRIME Protocol;
- Prime Alignment, Decomposition & Feedback;
- Aligned Instruction & Learning Envelopes;
- PARCELS Layer Architecture;
- Restricted Cargo Handling where package content affects scope.

---

### 9.2 Module 02 — Route Operations

**System Question:** Where should this package go, and under what conditions may it move?

**Terminal Objective:**  
Given a valid bounded package and declared requirements, the learner can choose or construct a governed route, identify dependencies and stop conditions, and distinguish routing from execution, verification, and release.

**Enabling Objectives:**

The learner can:

1. distinguish route from movement;
2. identify route requirements;
3. identify dependencies;
4. recognize route-blocking unknowns;
5. define escalation conditions;
6. identify retry and failure conditions;
7. distinguish route eligibility from handler prestige;
8. identify when a package requires HOLD;
9. distinguish execution routing from verification routing;
10. preserve authority boundaries during route selection.

**Primary Doctrine Dependencies:**

- PRIME;
- Shipping Label & Classification;
- Restricted Cargo Handling;
- Evidence & Verification Architecture;
- Bounded Autonomy & Execution Envelopes.

---

### 9.3 Module 03 — Facility Operations

**System Question:** How do multiple packages move safely through one operational environment?

**Terminal Objective:**  
Given a mixed inbound set of packages, the learner can receive, validate, classify, stage, hold, quarantine, and dispatch packages according to label state, handling requirements, facility capacity, and authorization boundaries.

**Enabling Objectives:**

The learner can:

1. distinguish inbound from ready-for-routing state;
2. validate package identity and label requirements;
3. classify handling state;
4. apply STANDARD / SENSITIVE / RESTRICTED / QUARANTINED / PROHIBITED states;
5. select ROUTE / HOLD / REFUSE / SANITIZE→RECLASSIFY disposition where supported;
6. distinguish capability from authorization;
7. preserve minimum-necessary cargo;
8. manage staging and queue state;
9. recognize capacity and flow constraints;
10. dispatch only eligible packages.

**Primary Doctrine Dependencies:**

- Shipping Label & Classification;
- Restricted Cargo Handling;
- PARCELS;
- Evidence & Verification;
- PRIME.

---

### 9.4 Module 04 — Transfer Operations

**System Question:** How does work change custody without losing what governs it?

**Terminal Objective:**  
Given a package that must cross handler or session boundaries, the learner can construct a valid handoff preserving package identity, required context, authority constraints, evidence, dependencies, and return conditions.

**Enabling Objectives:**

The learner can:

1. distinguish continuing one package from creating a handoff package;
2. identify required context;
3. exclude irrelevant context;
4. preserve ownership and authority constraints;
5. preserve evidence and provenance;
6. define consolidation boundaries;
7. identify dependency-independent parallel work;
8. recognize stale context;
9. construct return routes;
10. prevent authority from expanding across a handoff.

**Primary Doctrine Dependencies:**

- PRIME Handoff & Context Routing;
- Bounded Autonomy;
- Restricted Cargo Handling;
- Evidence & Verification;
- Prime Alignment, Decomposition & Feedback.

---

### 9.5 Module 05 — Transport Coordination

**System Question:** What handling capability and route does this package require?

**Terminal Objective:**  
Given a labeled package and available handler classes, the learner can match package requirements to capability, placement, locality, cost, latency, boundary, and verification requirements without conflating placement, capability, permission, or authority.

**Enabling Objectives:**

The learner can:

1. read capability requirements from a Shipping Label;
2. distinguish placement from capability;
3. distinguish capability from permission;
4. interpret locality and data-boundary requirements;
5. interpret cost and latency constraints;
6. identify prohibited handlers or destinations;
7. distinguish execution route from verification route;
8. apply escalation policy;
9. justify handler selection from package requirements;
10. reject prestige-based routing.

**Primary Doctrine Dependencies:**

- Shipping Label & Classification;
- Restricted Cargo Handling;
- Evidence & Verification;
- Bounded Autonomy;
- PRIME.

---

### 9.6 Module 06 — High-Control Operations

**System Question:** What additional controls are required when consequence increases?

**Terminal Objective:**  
Given a higher-consequence package, the learner can design an execution and verification plan whose confinement, observability, review independence, evidence strength, and release controls are proportional to the package's consequence.

**Enabling Objectives:**

The learner can:

1. define an execution envelope;
2. identify minimum substrate;
3. constrain network, filesystem, credentials, time, and cost;
4. identify when stronger verification is required;
5. prefer deterministic evidence where available;
6. distinguish build capability from review capability;
7. distinguish evaluation from release;
8. identify appropriate negative controls or comparators;
9. preserve human release authority where required;
10. expose uncertainty as state rather than fabricate completeness.

**Primary Doctrine Dependencies:**

- Bounded Autonomy & Execution Envelopes;
- Evidence & Verification Architecture;
- Restricted Cargo Handling;
- PRIME;
- Release QA.

---

### 9.7 Module 07 — Network Orchestration

**System Question:** How are many packages and handlers governed as one accountable system?

**Terminal Objective:**  
Given a multi-package operational scenario, the learner can coordinate manifests, resource states, dependencies, queues, parallel work, capacity, verification, holds, escalation, consolidation, and release while preserving manageable control and doctrine boundaries.

**Enabling Objectives:**

The learner can:

1. distinguish package state from resource state;
2. build a manifest;
3. identify dependency-independent work;
4. limit parallelism to governable scope;
5. coordinate consolidation boundaries;
6. track resource availability;
7. identify bottlenecks and blocked states;
8. prioritize packages under constraints;
9. preserve execution/verification independence;
10. coordinate release only after delivery is established;
11. apply PARCELS to locate dominant failure modes;
12. operate PRIME across a network rather than one package.

**Primary Doctrine Dependencies:**

- PRIME Protocol Orchestration;
- PARCELS;
- Bounded Autonomy;
- Shipping Label;
- Restricted Cargo Handling;
- Evidence & Verification;
- Prime Alignment, Decomposition & Feedback.

## 11. Module 07 Resource-State Model

Module 07 introduces a formal instructional resource-state model.

~~~text
REGISTERED
AVAILABLE
ASSIGNED
ACTIVE
HELD
RELEASED
OUT_OF_SERVICE
~~~

### REGISTERED

Known to the resource system.

### AVAILABLE

Eligible to receive assignment under current conditions.

### ASSIGNED

Bound to a specific package, route, manifest, or role.

### ACTIVE

Currently performing the assigned work.

### HELD

Temporarily unavailable or prevented from movement or assignment pending resolution.

### RELEASED

No longer committed to the completed assignment and returned to the appropriate pool or terminal state.

### OUT_OF_SERVICE

Not eligible for operational assignment.

These are training-control states and do not supersede implementation-specific state machines.

## 12. Module 07 Span-of-Control Principle

The program teaches a bounded orchestration rule:

> **Do not create more lanes than the manifest can govern.**

Instructionally, span of control means the orchestrator must maintain enough observability and decision quality to govern active work.

When flat coordination becomes unmanageable, the learner should restructure the work rather than add uncontrolled parallelism.

The program does not prescribe a universal numeric ratio.

The instructional question is whether the current orchestration structure preserves:

- package identity;
- responsibility;
- state visibility;
- dependency control;
- consolidation;
- verification;
- escalation;
- recovery.

## 22. Assessment Model

Assessment is continuous and cumulative.

Each module uses:

~~~text
INSTRUCTION
      ↓
KNOWLEDGE CHECK
      ↓
CLASSIFICATION / JUDGMENT TASK
      ↓
WORKBOOK PERFORMANCE
      ↓
MODULE QUIZ
      ↓
LEARNER-STATE UPDATE
~~~

### 22.1 Evidence types

Assessment should distinguish:

**Recall**  
Can the learner identify the concept?

**Classification**  
Can the learner recognize the correct state, rule, boundary, or disposition?

**Application**  
Can the learner choose and justify the correct operational action?

**Performance**  
Can the learner produce the required operational artifact or decision under constraints?

Applied evidence should carry more weight than self-report.

### 22.2 Program rule

> **QUIZ PASS ≠ OPERATOR QUALIFICATION.**

Passing module quizzes establishes only one evidence stream.

## 28. Remediation

Remediation is route correction, not punishment.

A learner who fails to demonstrate an objective should be routed to the smallest instructional package that addresses the observed gap.

Possible remediation outputs include:

- targeted Student Manual section;
- selected podcast segment;
- selected visual;
- repeat workbook task;
- alternate worked example;
- supervised practice;
- reassessment.

The program should not require complete restart when the failure is bounded and local.

## 31. Release Requirements

The POI has its own release lifecycle.

A Candidate POI may not become Canonical Training Material until:

- doctrine dependencies are current;
- all seven module objectives are adjudicated;
- module ABI is complete;
- artifact matrix is complete;
- assessment model is approved;
- qualification standard is approved;
- terminology is guard-clean;
- cross-media traceability rules are established;
- release ledger is complete.

The POI must be versioned.

Any module-level change that affects terminal objectives, enabling objectives, qualification evidence, required artifacts, or doctrine dependencies requires a POI change or formally compatible amendment.
